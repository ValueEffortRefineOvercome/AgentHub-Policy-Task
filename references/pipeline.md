# 작업 파이프라인 7 단계 — 상세

`SKILL.md` 1절의 각 단계가 무엇을 확인하고 무엇을 적는지. 작업을 시작할 때 읽는다.

원칙 하나: **각 단계는 산출물을 남긴다.** 남지 않으면 그 단계를 지난 적이 없다.

---

## 1. Intake — 해석과 유형 분류

### 적는 것
```
범위: <요청을 한 문장으로. 요청자의 말이 아니라 내가 이해한 것>
유형: <아래 표에서 하나>
```

### 작업 유형

| 유형 | 무엇 | 깊어지는 단계 | 얕아지는 단계 |
|---|---|---|---|
| `조회` | 읽기만. 아무것도 안 바꾼다 | Context | Planning · Execution · Documentation |
| `조사` | 원인·현황을 알아낸다 | Context · Validation | Execution · Documentation |
| `수정` | 있는 것을 고친다 | Validation(회귀) | Planning |
| `신규` | 없던 것을 만든다 | Planning · Validation(예외) | — |
| `운영` | 배포·설정·저장소 조작 | Validation · Reporting | Planning |
| `문서` | 문서만 바꾼다 | Documentation | Execution · Validation(회귀) |

유형이 둘로 갈리면 **깊은 쪽**을 택한다. 조회인 줄 알았는데 고쳐야 하면 Intake 로
돌아가 유형을 바꾸고 적는다 — 유형이 바뀐 사실이 Reporting 에 남아야 한다.

### 멈추는 조건
해석이 둘로 갈리고 **결과가 달라지면** 여기서 1 줄 질문하고 멈춘다 (`SKILL.md` 2절).
갈리지만 결과가 같으면 가정을 적고 진행한다.

---

## 2. Context — 관련 코드·문서 확인

### 적는 것
```
파일: <건드릴 파일과 그 호출부. 저장소 상대경로>
문서: <관련 REQ·ARCH·ADR·ISSUE 의 ID, 또는 "없음">
재사용: <이미 있는 것으로 되는지. 되면 Planning 이 짧아진다>
```

### 확인 순서
1. **이 저장소에 이미 있나** — 같은 일을 하는 함수·스크립트·설정
2. **호출부 전부** — 고칠 함수를 누가 부르는지. 한 곳만 고치면 형제 호출부가 남는다
3. **관련 문서** — `/doc-policy` 로 ADR·REQ·ISSUE 를 찾는다.
   이미 기각된 접근을 다시 하지 않기 위해서다

### 금지
- 파일 전체 읽기. `grep` · `sed -n 'a,bp'` 로 범위를 좁힌다
- 호출부를 안 보고 "최소 diff" 라고 부르기 — 범위를 모르면 그건 두 번째 버그다

---

## 3. Planning — 실행 가능 단위로 분해

### 적는 것
```
- [ ] <단위 1 — 무엇이 참이면 됐나>
- [ ] <단위 2>
되돌릴 수 없는 것: <있으면 표시. 없으면 "없음">
```

### 단위의 기준
**하나의 단위 = 하나의 판정 가능한 변경.** "됐다" 를 사람이 아니라 명령이나 관찰로
판정할 수 있어야 한다. 체크박스로 안 떨어지면 단위가 너무 크다.

### 순서
- 되돌릴 수 없는 작업은 **마지막에** 둔다. 앞에 두면 앞 단계 실패가 비싸진다
- X 등급(`/agent-policy` 2절)은 그 단위 직전에 사람 확인을 받는다
- 의존이 있으면 순서를 고정하고, 없으면 병렬로 둔다

### 유형별
`조회` · `조사` 는 "단일 조회, 분해 불필요" 한 줄로 통과한다.
`신규` 는 가장 깊다 — 없던 것은 경계가 안 정해져 있어 분해가 곧 설계다.

---

## 4. Execution — 수행

### 규칙
- 계획 순서대로. 단위마다 **커밋 가능한 상태**로 둔다
- 최소 diff. 요청 범위 밖 수정 금지
- 계획에서 벗어나면 **3 단계로 돌아가 계획을 고친다.** 조용히 벗어나지 않는다
- 같은 실패 2 회면 멈추고 보고 (`/agent-policy` 5절)

### 적는 것
계획 체크박스를 채운다. 벗어난 단위는 그 이유를 한 줄.

---

## 5. Validation — 요구사항 · 회귀 · 예외

**세 축을 각각 적는다.** 하나라도 비면 검증이 아니다.

| 축 | 무엇을 보나 | 어떻게 |
|---|---|---|
| 요구사항 | 1 단계의 한 문장이 됐나 | 그 문장을 다시 읽고 대조한다 |
| 회귀 | 원래 되던 것이 여전히 되나 | `/pipeline-policy` 1절 게이트 전부 |
| 예외 | 경계·실패 경로가 어떻게 되나 | 유형마다 다르다 — 아래 표 |

### 예외 축은 유형마다 다르다

| 유형 | 예외로 봐야 할 것 |
|---|---|
| `수정` · `신규` | 빈 입력 · 없는 파일 · 권한 없음 · 네트워크 없음 · 경계값 |
| `문서` | **적은 것이 사실인가** — 가리키는 파일이 실재하나, 적은 명령이 실제로 도나 |
| `운영` | 되돌릴 수 있나 · 중간에 끊기면 어떻게 되나 |
| `조회` · `조사` | 본 범위가 결론을 지탱하나 — 일부만 보고 전체라고 말하지 않았나 |

`문서` 유형에 코드 기준(빈 입력·권한)을 적용하면 전부 "해당 없음" 이 되고 검증이
비어버린다. **문서는 거짓말할 수 있고 그게 그 유형의 실패 경로다.**

### 적는 것
```
요구사항: <됐다 / 일부 — 무엇이 안 됐나>
회귀:     <게이트 결과. 돌린 명령과 출력 요약>
예외:     <확인한 경로, 또는 "해당 없음 — 왜">
```

### 금지
- **돌리지 않고 "통과" 라고 쓰기.** 안 돌렸으면 "안 돌렸다" 다
- 실패를 요약에서 빼기. 실패는 출력과 함께 그대로 적는다
- 테스트 0 개를 통과로 세기 (`pytest` exit 5 는 통과가 아니다)
- "예외 없음" 을 근거 없이 쓰기 — 왜 해당 없는지가 근거다

---

## 6. Documentation — 문서 갱신

이 단계가 없으면 **결정이 대화에만 남는다** (`SKILL.md` 5절 금지).
다른 PC 의 새 세션은 그 결정을 모른다.

### 라우팅 — 무엇이 생겼으면 무엇을 쓰나

| 이번 작업에서 | 쓸 문서 |
|---|---|
| 되돌리기 비싼 선택을 했다 | **ADR** |
| 요구사항이 바뀌거나 새로 생겼다 | **REQ** |
| 구조·경계를 정했다 | **ARCH** |
| 문제를 찾았지만 지금 안 고친다 | **ISSUE** |
| 검증 범위를 정리할 가치가 있다 | **TEST** |
| 떠오른 생각이 있다 | `docs/IDEA-INBOX.md` 한 줄 |
| 위 어느 것도 아니다 | **"없음"** 이라고 적는다 |

종류·이름·상태는 `/doc-policy`. 번호는 `bin/next-id.sh`.

### 적는 것
```
문서: <만들거나 고친 ID 목록, 또는 "없음">
```

### 판단 기준
커밋 메시지 한 줄로 끝나는 변경에는 문서를 만들지 않는다. 문서는 **diff 가 말하지
않는 것** — 왜 그렇게 했고 무엇을 버렸는지 — 이 있을 때만이다.

## 7. Reporting — 사람이 확인할 요약

형식은 `SKILL.md` 3절. 단계별 산출물을 그 네 칸으로 접는다.

| 3절 칸 | 어느 단계에서 오나 |
|---|---|
| 결과 | 1 단계 한 문장 + 됐는지 |
| 변경 | 4 단계 + 6 단계 문서 ID |
| 검증 | 5 단계 세 축 |
| 남은 것 | 3 단계 미완 체크박스 + 범위 밖 발견 |

### 반드시 적는 것
- **유형이 바뀌었으면** 그 사실 (조회로 시작해 수정이 됐다 등)
- **단계를 되돌아갔으면** 어디서 어디로, 왜
- **검증을 안 돌렸으면** 안 돌렸다고. "없음" 과 "안 함" 은 다르다

### 길이
요약이 변경보다 길면 요약을 줄인다. 요청하지 않은 설명은 넣지 않는다.

---

## 단계 산출물은 어디에 남나

**PR 본문에 7 단계를 다 적지 않는다.** 대부분은 이미 영구 기록으로 간다.

| 단계 | 영구히 남는 곳 |
|---|---|
| 1 Intake | PR 본문 `목표` — 범위 한 문장 + **유형 한 단어** |
| 2 Context | PR 본문 `접근` — 재사용 판단과 버린 접근만. 읽은 파일 목록은 안 남긴다 |
| 3 Planning | PR 본문 `접근`(택한·버린 분해) + `다음`(미완 체크박스) |
| 4 Execution | **커밋과 diff.** PR 본문에 다시 적지 않는다 |
| 5 Validation | **게이트 명령 자체.** 이어받는 쪽은 다시 돌리면 된다 |
| 6 Documentation | **그 문서 자체** (ADR·ISSUE·REQ). ID 는 커밋 메시지에 |
| 7 Reporting | 대화. 사라져도 되는 것 |

### 왜 다 안 넣나
PR 본문은 **이어받기 위한 문서**다 (`consistency.md`). 다른 PC 의 새 세션에 필요한 건
의도와 남은 일이고, 코드·게이트 결과·문서는 저장소에 이미 있다. 다 넣으면 같은 내용이
두 곳에 살고 한쪽이 낡는다.

### `SKILL.md` 5절 금지와의 관계
"결정을 세션 대화에만 남기기" 금지는 지켜진다 — **결정은 전부 영구 기록으로 간다.**
접근과 버린 선택지는 PR 본문, 되돌리기 비싼 선택은 ADR, 미룬 문제는 ISSUE.
대화에만 남는 것은 중간 상태이고 그건 사라져도 되는 종류다.

판단이 남을 가치가 있는데 갈 곳이 없으면 그건 문서가 필요하다는 신호다 — Validation 의
"예외 해당 없음, 왜냐하면 ..." 이 중요하면 그건 TEST 문서의 "덮지 않은 범위" 다.
